ChatGPT · Health OpenAI 2026.07.23
  • 健康上下文从「专属页」进入「任意对话」（07.23）—— 官方博客记录，早期测试中超七成健康对话发生在独立 Health 页之外，因此改为:连接后可在任何对话中调用健康信息，也保留 Health 作为连接与管理的「主基地」。
  • 默认「先授权再使用」+ @Health 显式召唤（07.23）—— ChatGPT 使用健康信息个性化回答前会先征询许可，用户可逐次批准或选择「始终允许」（设置 > 插件 > Health）;也可在消息里加 @Health 主动带入上下文。
  • 连接项可审阅、可增删、可断开（07.23）—— 可连接 Apple Health 与医疗记录（如 One Medical、Function 等），并审阅已连接的病症 / 用药、删除无关项、补充家族史;断开某来源后，同步数据将在 30 天内从系统删除。
  • 隐私承诺写进产品说明（07.23）—— 官方称对话在传输与静态存储中加密、Health 信息额外加密，连接的健康数据不用于训练基础模型、不用于广告;健康信息默认不自动生成 memory，可用 Temporary Chat 规避留痕。
Health in ChatGPT 是本周最值得拆解的一次「敏感能力产品化」，提炼三条:① 敏感能力的正确形态是「上下文跟着人走」，而不是把用户困在专属页里——OpenAI 的关键改动，是承认「超七成健康对话发生在专属页之外」这一真实行为，于是让健康上下文可被任意对话调用、专属页退居「连接与管理主基地」;做垂直能力别急着造一个独立 tab，先看用户到底在哪儿用。② 越敏感的数据，「授权粒度」越要做细——先授权再使用、可逐次批准或「始终允许」、可 @Health 显式召唤，这套组合把「什么时候用我的数据」的控制权交回用户手里;敏感场景的默认态应是「保守 + 可逐项放开」。③ 连接、审阅、断开、删除要形成闭环——可增删连接项、可断开来源并 30 天内删除、默认不自动生成 memory，这些不是隐私条款里的小字，而应是界面上可见、可操作的一等能力。垂直能力优先「上下文跟随对话」而非独立 tab（专属页只做连接 / 管理主基地）;敏感数据默认「先授权再使用」，支持逐次批准 / 始终允许;显式召唤入口（@Health）与被动调用并存，用户可控;连接项可审阅 / 增删 / 断开，断开后有明确删除时限（如 30 天）;敏感对话默认不自动留 memory，提供 Temporary Chat 选项;隐私承诺（不训练 / 不投广告 / 额外加密）要在界面可见，而非仅写进条款。
来源：openai.com · Launching Health in ChatGPT · The Verge · OpenAI rolls out ChatGPT Health
Claude · 语音模式 Anthropic 2026.07.23
  • 语音模式不再锁死在小模型，可选 Opus / Sonnet / Haiku（07.23）—— 官方博客宣布语音模式解绑「只能用 Haiku」的限制:可在 Opus、Sonnet、Haiku 间切换，让「用语音思考难题」成为可能，而不只是用来做轻量问答。
  • 对话中途可换模型，默认沿用文字聊天的选择（07.23）—— 语音会话默认继承你在文字聊天里选的模型，且可在同一段对话里随时切换;把「选模型」这件事从一次性设置，变成随任务难度即时调节的旋钮。
  • 接入已连接工具，用前逐次征询许可（07.23）—— 语音模式可调用 Gmail、日历、Slack、Canva、Notion 等已连接工具，但每次动用前都会先征询许可;能力放开的同时把「授权」留在用户手里。
  • 10+ 语言可手动指定，beta 覆盖全平台（07.23）—— 支持十余种语言并可手动指定当前语言;功能以 beta 形式在移动端与桌面端铺开，Free 档可用 Haiku + 1 个工具，付费档解锁全部模型与全部工具。
Claude 把语音模式从「只能用小模型的轻量入口」升级为「可选模型 + 可接工具」的一等交互面，提炼三条:① 语音不该被降级为「简化版助手」，能力要与文字端拉齐——过去语音常被默认绑定最快最轻的模型，等于告诉用户「认真的事别用语音」;Claude 让 Opus / Sonnet 也能进语音，是承认语音是完整的思考媒介，而非快捷玩具。② 「选模型」应从一次性设置变成随任务调节的旋钮——默认继承文字端选择、对话中可随时切换，把「用多强的脑子」交给用户按当前难度即时决定;凡是多档能力的产品，都该让档位切换轻到「随手可调」。③ 语音接入工具时，授权要「逐次征询」而非一次放开——语音交互更快、更口语，越要在动用 Gmail / 日历 / Slack 这类敏感工具前逐次确认;交互越顺滑，越要给关键动作留一道「明确同意」的闸。语音与文字端能力拉齐（可选 Opus / Sonnet，非只给最轻模型）;「选模型」从一次性设置变随任务即时切换的旋钮;语音默认继承文字端选择，降低重复配置成本;语音调用敏感工具前逐次征询许可（顺滑 ≠ 免确认）;能力分档清晰（Free = Haiku + 1 工具 / 付费 = 全模型 + 全工具）;多语言支持可手动指定，避免自动识别误判。

企业级 AI 平台
Claude Opus 5 · on Amazon Bedrock Anthropic × AWS 2026.07.24
  • 迄今最强 Opus 登陆 Bedrock（07.24）—— AWS What's New 记录 Anthropic Claude Opus 5 在 Amazon Bedrock 可用，被描述为「最先进的 Opus 模型」，面向企业级智能任务。
  • 零数据保留（ZDR）默认开启（07.24）—— 关键点在于 ZDR 是「默认态」而非需要企业自行申请或配置的可选项;顶级能力与「数据不被保留」的治理承诺被打包在同一层交付。
  • 「能力」与「治理」同层呈现—— 对受合规约束的企业而言，模型上线信息里同时讲清「有多强」和「数据怎么处理」，比只讲跑分更能推动采购决策。
Opus 5 以「ZDR 默认开启」的姿态上 Bedrock，给企业级 AI 两条硬原则:① 数据治理要做成「默认安全」，而不是「可选加固」——把零数据保留设为默认态，等于把最保守的选项预置给企业，用户不必去翻设置、提工单才能拿到合规基线;凡涉及企业数据去向的开关，默认应偏保守，让「更安全」成为不作为时的结果。② 模型上线信息要「能力 + 治理」双栏并陈——企业选型看的从来不只是跑分，而是「这么强的模型，会不会留我的数据、留多久、能不能关」;把数据处理承诺与能力指标放在同一张卡片里讲清，才是面向 B 端的正确叙事。第三条:治理承诺要可验证、可审计，而非仅停留在发布稿的形容词里。数据治理默认安全（ZDR 默认开），而非「可选加固 / 需申请」;模型上线页「能力指标 + 数据处理承诺」双栏并陈;企业数据去向开关默认偏保守（不作为 = 更安全）;治理承诺可验证 / 可审计（不止发布稿形容词）;跨云 / 跨模型的 ZDR 状态在控制台一眼可查;合规基线作为默认交付项，而非事后配置项。
来源：aws.amazon.com · Claude Opus 5 is now available on AWS

  • 默认不用于训练 + 专业连接器（07.29）—— 内容默认不用于训练模型;配套 75+ 生命科学 skills 与文献 / 数据库连接器，让通用助手贴合科研工作流。

Amazon Bedrock AgentCore · 统一可观测性 AWS 2026.07.23
  • trace、prompt 与日志进同一 log group（07.23）—— AWS What's New 记录 AgentCore 将 agent 的 traces、prompts 与运行日志合并进单个按 agent 划分的 Amazon CloudWatch log group，调试时不必在多处拼数据。
  • 细粒度访问控制 + CMK 加密（07.23）—— 统一到一处的同时，支持按 agent 施加 fine-grained access control 与客户托管密钥（CMK）加密，兼顾「集中」与「可管控」。
  • 把「Agent 排障」收敛为一条时间线—— 从「想了什么（prompt）、做了什么（trace）、系统发生了什么（logs）」到同源可查，让 Agent 的可观测性成体系。
AgentCore 把 Agent 的运行链路收敛到一处，印证 Agent 产品的一条底层 UX 走向:① Agent 的可观测性要「一处可查」，把 trace / prompt / 日志拼在一起——Agent 的问题往往横跨「它想了什么（prompt）、做了什么（trace）、系统发生了什么（logs）」三层;把它们放进同一 log group，等于把调试从「跨面板拼图」变成「顺着一条时间线读」。做 Agent 平台，可观测性不是附属功能，而是决定用户敢不敢把关键流程交给 Agent 的前提。② 「集中」必须与「可管控」同时给——把数据收拢到一处很方便，但敏感的 prompt / trace 也随之集中，因此 fine-grained access control + CMK 加密不是加分项而是配套底线;越是统一观测，越要把「谁能看、怎么加密」讲清楚。第三条:统一 log group 应按 agent 划分，让「按 agent 施加访问控制」成为默认粒度，而非全局一把梭。Agent 可观测性「一处可查」:prompt（想了什么）+ trace（做了什么）+ logs（系统状态）同源;集中观测同时配 fine-grained access control + CMK 加密（集中 ≠ 失控）;调试从「跨面板拼图」变「顺时间线读」;可观测性作为「敢把关键流程交给 Agent」的前提，而非附属功能;log group 按 agent 划分，访问控制粒度对齐到 agent;敏感 prompt / trace 的可见范围默认最小化。

Figma · 用 Agent 守护代码安全 Figma 2026.07.24
  • 一份 policy 贯穿「编写 → PR 评审 → 历史审计」三阶段（07.24）—— 官方 blog 记录 Figma 的安全 Agent 在代码写就时守护、评审每一个 PR、审计十年老 monorepo，全部基于同一份 policy;这份 policy 由「precedents（示例）」而非宽泛规则构成，像「新人第一天该读的完整威胁模型」。
  • 双模型交叉 + adjudicator 复核（07.24）—— PR 评审并行运行 Claude Code（Opus 4.8）与 Codex（GPT-5.6 Sol），两者能抓到不同的 bug;对「边缘性驳回」再由一个 adjudicator Agent 复核，以提升召回。
  • 精度稳定超 70% 才对开发者可见（07.24）—— 面向开发者的 PR 评论，只有在 precision（上报中真实漏洞的占比）持续高于 70% 后才启用;作者可对每条发现给「有用 / 无用」反馈，作为精度信号;单次 PR 评审中位成本约 $0.50。
Figma 这篇工程实践，虽讲的是安全，却给「AI 参与协作流程」立了三条可迁移的 UX 原则:① AI 的建议要过「精度门槛」才对人可见——宁可先沉默，也不要用噪声消耗信任——Figma 把「precision 稳定超 70%」作为对开发者暴露评论的开关，这正是 AI 辅助最关键的产品判断:一旦让用户被误报淹没，再准的后续建议也会被无视;可见性应由质量指标闸控，而非「先上了再说」。② AI 参与协作要有「反馈闭环」，把人的判断喂回系统——作者对每条发现的「有用 / 无用」直接成为精度信号;凡是 AI 介入的人机协作，都该给一个轻量、就地的反馈入口，让系统的准确度随使用而收敛。③ 规则要写成「示例（precedents）」而非抽象条文，并做「新人可读」的门槛——把 policy 定义成一组可读的判例、要求它像「新人第一天能读懂的威胁模型」，本质是让 AI 的判断依据可被人理解、可被审阅;设计 AI 的「知识源」时，可读性和可维护性和准确率同等重要。AI 建议由「精度门槛」闸控可见性（precision 达标才对人暴露，宁缺毋滥）;每条 AI 发现配就地「有用 / 无用」反馈，喂回精度信号;规则写成可读「示例 / 判例（precedents）」而非抽象条文;知识源以「新人第一天可读懂」为可维护性门槛;多模型交叉 + adjudicator 复核边缘 case（提召回、控误伤）;单次评审成本可见（如中位 $0.50），让「AI 辅助」有明确性价比。

AI 原生入口

OpenAI 官方动态 · 垂直能力入口 — 从通用助手到场景化入口的定位动作

OpenAI · Health 作为「场景化入口」 OpenAI（openai.com/news） 2026.07.23
  • 把「每周 3 亿人的健康提问」变成产品入口（07.23）—— 官方博客以「每周超 3 亿人向 ChatGPT 提健康问题」为切口，把一个高频真实需求收敛成可连接数据、可管理的 Health 入口。
  • 入口形态随真实行为调整（07.23）—— 因超七成健康对话发生在专属页之外，OpenAI 让能力「跟随对话」而非困在独立 tab;入口设计以真实使用路径为准，而非产品经理设想的路径。
  • 信任建设作为扩张前置件（07.23）—— 加密、不训练、不投广告、可断开即删等承诺被放在发布叙事的核心位置;把垂直入口的普及建立在「先讲清安全」之上。
从「AI 原生入口」视角看 Health，看点不在健康本身，而在「通用助手如何长出场景化入口」，提炼三条:① 场景入口要从「用户已经在做的高频真实行为」里长出来——3 亿人本就在问健康问题，OpenAI 做的是把这条既有需求收敛成可连接、可管理的入口，而非凭空造需求;找垂直入口，先看用户已经把通用助手当什么用。② 入口形态以「真实使用路径」为准，敢于推翻最初设计——发现七成对话发生在专属页之外，就让能力跟随对话、专属页退居管理台;好入口是被真实行为校正出来的，不是一次设计定死的。③ 垂直入口越敏感，「信任」越要前置——把加密 / 不训练 / 不投广告 / 断开即删放在叙事核心，是把信任建设放在增长之前;入口越普及、数据越敏感，越要先回答「谁能用、数据去哪、怎么撤回」。场景入口从「用户已在做的高频真实行为」中长出（非凭空造需求）;入口形态以真实使用路径校正（敢推翻「独立 tab」的初始设计）;敏感垂直入口把「信任叙事」（加密 / 不训练 / 不投广告 / 断开即删）前置于增长;通用助手 → 场景入口时保留「主基地」做连接与管理;高频需求收敛为「可连接 + 可管理」而非一次性问答;扩张前先答清「谁能用 / 数据去哪 / 怎么撤回」。

对我们的启示

从 07.23 ~ 07.29 这一周产品动态中提炼的 6 条具体、可执行的设计建议

Insight · 01
↗ Health in ChatGPT · 上下文跟随对话
垂直能力要「跟着人走」，别把用户困在专属页
Health in ChatGPT 最关键的改动，是承认「超七成健康对话发生在专属页之外」，于是让健康上下文可在任意对话被调用、专属页退居「连接与管理主基地」:① 做垂直能力别急着造一个独立 tab——先看用户到底把通用助手当什么用、在哪儿用;能力应长在用户已有的路径上，而不是逼用户绕到新入口。② 入口形态要被真实使用行为校正——发现路径不对就敢推翻最初设计，让能力跟随对话;好入口是「测出来 + 改出来」的，不是一次拍板定死的。专属页不必消失，但它的角色应从「唯一入口」退为「连接 / 管理主基地」。垂直能力优先「上下文跟随对话」而非独立 tab;入口形态以真实使用路径校正（敢推翻初始设计）;专属页退为「连接 / 管理主基地」，不做唯一入口;先看「用户把通用助手当什么用」再决定入口;高频需求收敛为「可连接 + 可管理」;能力长在既有路径上（减少绕路成本）。
Insight · 02
↗ Health in ChatGPT · 授权与数据可控
越敏感的数据，「授权粒度」和「删除闭环」越要做细
Health 把「什么时候用我的数据」的控制权尽量交回用户:先授权再使用、可逐次批准或「始终允许」、可 @Health 显式召唤，连接项可审阅 / 增删 / 断开、断开后 30 天内删除、默认不自动生成 memory:① 敏感场景的默认态应是「保守 + 可逐项放开」——不默认全量使用，而是先问、可细调;掌控感在处理个人 / 健康数据时高于便利性。② 连接、审阅、断开、删除要形成可见闭环——这些不该是隐私条款里的小字，而应是界面上可操作的一等能力;「我的数据在哪、怎么撤回」要一眼可查。第三条:加密 / 不训练 / 不投广告等承诺要在界面呈现，而非仅写进 ToS。敏感数据默认「先授权再使用」，支持逐次批准 / 始终允许;显式召唤（@Health）与被动调用并存，用户可控;连接项可审阅 / 增删 / 断开，断开后有明确删除时限（如 30 天）;敏感对话默认不自动留 memory，提供 Temporary Chat;隐私承诺（不训练 / 不投广告 / 额外加密）界面可见;「数据在哪 / 怎么撤回」一眼可查（不藏深层菜单）。
Insight · 03
↗ Figma 安全 Agent · 精度门槛决定可见性
AI 建议要过「精度门槛」才对人可见，宁缺毋滥
Figma 的安全 Agent，只有在 precision（上报中真实漏洞占比）持续高于 70% 后，才对开发者启用 PR 评论，且作者可对每条发现给「有用 / 无用」反馈:① 可见性应由质量指标闸控，而非「先上了再说」——AI 辅助最致命的失误，是让用户被误报淹没;一旦信任被噪声消耗，再准的后续建议也会被无视。给 AI 建议设一道「达标才暴露」的闸门，是保护信任的关键产品判断。② AI 参与协作要有轻量、就地的反馈闭环——把人的「有用 / 无用」判断喂回系统作为精度信号，让准确度随使用收敛;凡 AI 介入的人机协作，都该在建议旁给一个一键反馈入口。AI 建议由「精度门槛」闸控可见性（达标才对人暴露）;可见性由质量指标决定，而非「先上线再优化」;每条 AI 发现配就地「有用 / 无用」反馈，喂回精度信号;误报治理优先级高于「多报」（噪声消耗信任）;精度不足时宁可沉默，也不淹没用户;反馈入口轻量、就地、一键（降低反馈成本）。
Insight · 04
↗ Figma 安全 Agent · 策略即威胁模型
AI 的「知识源」要写成可读示例，并做「新人可读」门槛
Figma 让安全 Agent 基于同一份 policy 工作，这份 policy 由「precedents（示例 / 判例）」而非宽泛规则构成，像「新人第一天该读懂的完整威胁模型」，并用双模型交叉 + adjudicator 复核边缘 case:① 规则写成可读示例而非抽象条文——让 AI 的判断依据可被人理解、可被审阅、可被维护;设计 AI 的知识源时，可读性和可维护性和准确率同等重要。② 用「新人可读」当可维护性门槛——如果一份策略连新人都读不懂，它对 AI 和对团队都难以长期维护;知识源要经得起「人能读、能改、能对齐」。第三条:对边缘性判断做二次复核（adjudicator），在「多报」与「漏报」之间找平衡，提召回同时控误伤。AI 知识源写成可读「示例 / 判例（precedents）」而非抽象条文;以「新人第一天可读懂」为可维护性门槛;判断依据可被人理解 / 审阅 / 维护（可读性 = 准确率同级）;边缘 case 做二次复核（adjudicator），平衡召回与误伤;多模型交叉互补（不同模型抓不同问题）;策略即「团队与 AI 共读的威胁模型」，保持对齐。
Insight · 05
↗ Claude 语音模式 · 可选模型 + 可接工具
语音别做「简化版助手」，能力与授权都要与文字端拉齐
Claude 把语音模式从「只能用 Haiku 的轻量入口」升级为可选 Opus / Sonnet / Haiku、可接 Gmail / 日历 / Slack 等工具，且默认继承文字端选择、对话中可随时切换、动用工具前逐次征询许可:① 语音是完整的思考媒介，不该被默认降级为快捷玩具——过去语音常被绑定最快最轻的模型，等于告诉用户「认真的事别用语音」;让顶级模型也能进语音，是承认它值得承载复杂任务。② 「选模型」应从一次性设置变成随任务调节的旋钮——默认继承 + 对话中可切换，把「用多强的脑子」交给用户按当前难度即时决定;凡多档能力的产品，档位切换都该轻到「随手可调」。第三条:语音交互更快更口语，动用敏感工具前越要逐次确认——交互越顺滑，关键动作越要留一道「明确同意」的闸。语音与文字端能力拉齐（可选 Opus / Sonnet，非只给最轻模型）;「选模型」从一次性设置变随任务即时切换的旋钮;语音默认继承文字端选择，降低重复配置成本;语音调用敏感工具前逐次征询许可（顺滑 ≠ 免确认）;能力分档清晰（Free = Haiku + 1 工具 / 付费 = 全模型 + 全工具）;把语音视为完整思考媒介，而非快捷问答玩具。
Insight · 06
↗ Bedrock AgentCore + Claude Opus 5 ZDR
Agent 可观测性要「一处可查」，治理要「默认安全」
同一周，AWS 把 AgentCore 的 trace / prompt / 日志收进同一 log group，Claude Opus 5 上 Bedrock 则默认开启零数据保留（ZDR）——两条线合起来给 Agent 平台两条底层原则:① Agent 的可观测性要「一处可查」——Agent 的问题横跨「想了什么（prompt）、做了什么（trace）、系统发生了什么（logs）」，放进同源等于把调试从「跨面板拼图」变成「顺时间线读」;可观测性是「敢把关键流程交给 Agent」的前提，不是附属功能。② 数据治理要做成「默认安全」而非「可选加固」——ZDR 默认开、集中观测同时配 fine-grained access control + CMK 加密，意味着最保守选项被预置给用户;凡涉及企业数据去向，默认应偏保守，让「更安全」成为不作为时的结果。Agent 可观测性一处可查:prompt + trace + logs 同源;调试从「跨面板拼图」变「顺时间线读」;可观测性是「敢交付关键流程」的前提，非附属功能;数据治理「默认安全」（如 ZDR 默认开）而非可选加固;集中观测同时配 fine-grained access control + CMK（集中 ≠ 失控）;企业数据去向默认偏保守，治理承诺可验证可审计。
