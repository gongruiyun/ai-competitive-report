ChatGPT · 桌面端 26.727 OpenAI 2026.07.30
  • 内置浏览器地址栏「历史回访 + 无匹配转搜索」（07.30）—— 官方 changelog 记录：在内置浏览器地址栏输入即可回访浏览历史中的页面，无匹配时转 Google 搜索；浏览历史可在 Settings 管理，并可让 ChatGPT 在需要时检索这段历史帮你找回访问过的页面。
  • Chrome 扩展把「当前上下文」带进对话（07.30）—— 扩展支持 @提及打开的标签页、把页面高亮文本带入侧边 chat，还能对任意 YouTube 视频提问并秒级作答，网页右键即可「Ask ChatGPT」;把浏览器里的现成上下文低成本喂给助手。
  • 多仓库审阅：一处看各仓 diff，不再切视图（07.30）—— 在 multi-folder 项目里可看到所有仓库及各自改动的行，点 Review 即可跨仓库审阅 diff，不必在多个独立 review 视图间来回切换。
  • 生成图编辑：Focused / Canvas 双视图 + 跨图评论（07.30）—— 生成图可在 expanded viewer 中打开、在 Focused view 与 Canvas view 间切换，跨多张图加评论、挑出想要的，并在不离开对话的前提下发出 targeted edits;侧栏还新增 Activity view（Cmd/Ctrl+Opt+U）汇总近期需关注的会话。
这次桌面端更新看似是「浏览器 + 代码 + 图像」三件事的拼盘，但底层是同一条 UX 主张——让 AI 助手贴着用户已有的工作现场，而不是把人拽进一个新界面，提炼三条:① 上下文要「就地带入」，别让用户复制粘贴搬运——@提及标签页、带入高亮文本、右键 Ask ChatGPT，本质都是把「用户眼前正在看的东西」一键喂给助手;凡是要用户手动搬运上下文的地方，都是一个可被「就地带入」替代的摩擦点。② 多目标操作要「一处纵览」，消灭视图切换——多仓库 diff 收进一个 Review、生成图进一个 expanded viewer 跨图评论，都是把原本分散在多个面板的动作收敛到一屏;审阅 / 批处理类场景，「不用切来切去」本身就是核心体验。③ 编辑要「不离开主流程」——targeted edits 不离开对话、图像调整就地完成，减少「跳出去改完再回来」的断点;让修改发生在原地，是保持心流的关键。上下文「就地带入」优先（@提及 / 带入高亮 / 右键唤起），减少手动搬运;多目标操作「一处纵览」（多仓库 diff 收进一个 Review），消灭视图切换;编辑「不离开主流程」（targeted edits 就地完成），保持心流;浏览历史可管理、可被助手按需检索（历史即上下文源）;近期需关注会话汇总为 Activity view，降低「找回对话」成本;助手贴合用户已有工作现场，而非另造新界面。

DeepSeek-V4-Flash · 正式版 API DeepSeek 2026.07.31
  • 调用方式「零改动」升级，只换模型名（07.31）—— 官方 updates 记录正式版 API 进入公测，调用方式保持不变，只需把 model 名设为 deepseek-v4-flash;把「用上新能力」的迁移成本压到近乎为零。
  • Agent 能力大幅反超前代 Preview（07.31）—— 多项 benchmark 远超 V4-Pro-Preview:Terminal Bench 2.1 = 82.7、Cybergym = 76.7、DeepSWE = 54.4、Toolathlon verified = 70.3、DSBench-FullStack = 68.7;定位明确指向 Agent / 编程类任务。
  • 原生支持 Responses API 格式，专门适配 Codex（07.31）—— 原生对齐 Responses API 并针对 Codex 做适配（官方给出 Codex 集成配置文档）;把「接进现有 Agent 工具链」作为一等诉求。
  • 与 Preview 同架构同尺寸，仅重新后训练（07.31）—— 明确说明 0731 版与 V4-Flash-Preview 同架构同尺寸、仅重新做了后训练;本次只升级 V4-Flash API，V4-Pro API 与 APP/WEB 未变，V4-Pro 正式版将随后发布。
DeepSeek 这次「只升级 Flash 一条线、调用零改动」，对做平台 / API 型产品的团队有两条可迁移原则:① 能力升级要做成「零迁移成本」，让老代码原地享受新能力——保持调用方式不变、只换模型名，等于把「要不要升级」的决策摩擦降到最低;凡是让用户为了新版本改代码 / 重配置的升级，都会拖慢采用速度。② 与生态既有工具链对齐，比自定义协议更重要——原生支持 Responses API、专门适配 Codex，是承认用户已经站在某套 Agent 工具链上，主动去接对方而非要求对方来接自己;做开发者产品，「接得进现有工作流」的价值高于「协议更优雅」。第三条:分线升级要讲清「什么变了、什么没变」——明确「只升级 Flash、Pro 与 APP/WEB 不变、同架构同尺寸仅重训」，让用户精确评估影响面，而非笼统说「模型更新了」。能力升级做成「零迁移成本」（调用不变 / 只换模型名），降低采用摩擦;主动对齐生态既有工具链（Responses API / Codex），而非自造协议;分线升级讲清「变了什么 / 没变什么」（只升 Flash、Pro 不变、同架构仅重训）;面向 Agent / 编程场景明确定位，benchmark 与用途对齐;迁移文档就位（Codex 集成配置），让「接进现有工作流」有路径;正式版与 Preview 关系透明，便于用户评估影响面。

一个「粘贴超 10k 字符自动转附件」的小改动，藏着三条对做输入 / 编辑器类产品普适的 UX 原则:① 用默认行为替用户挡掉「隐性代价」——大段粘贴会悄悄吞掉 context window、拖累后续回答质量，普通用户根本感知不到;把它默认转成附件，是产品替用户挡下了一个看不见的坑。好的默认，应主动规避用户意识不到的负面后果。② 自动化必须留「一键还原」的退路——「Show in text field」保证自动转换不会变成强制;凡是替用户做决定的自动行为，都要配一个低成本的撤销 / 还原入口，让「智能」不等于「霸道」。③ 被验证的体验应「默认扩展」到高价值场景——先在其它档位跑通，再补齐到 Enterprise / Education，是把好体验一致地推给最需要治理 context 的企业用户;体验的一致性本身就是企业级信任的一部分。默认行为替用户挡掉「隐性代价」（大段粘贴吞 context window 不可感知）;自动化必配「一键还原」退路（Show in text field），智能 ≠ 霸道;被验证的体验「默认扩展」到高价值 / 强治理场景（Enterprise / Education）;输入区保持干净，长内容降级为可折叠附件;阈值清晰可预期（>10k 字符触发），行为不玄学;跨档位体验一致性作为企业级信任的一部分。

Amazon Bedrock · Web Search（GA） AWS 2026.08.04
  • 把 grounding 变成平台原生的 server-side 工具（08.04）—— AWS ML Blog 记录 Web Search 正式可用:模型识别到需要实时网络知识时，由 Bedrock 在服务端发起检索、把结果注入 context，全程无需客户端 tool-use 循环、外部 API 解析或重试。
  • 「加一个参数」即启用，免去供应商上手（08.04）—— 在既有 OpenAI 兼容 API 调用里加 tools=[{"type": "web_search"}] 即可开启，不需要 vendor onboarding、API key、编排层或独立 SDK;把「接搜索」这件重活收敛成一个参数。
  • 默认零数据外泄 + 结果自带引用（08.04）—— 检索全程在 Bedrock 基础设施内完成、默认零数据外泄以满足合规;返回结果带 url_citation 结构化引用注解（含标题与 URL），并接入 CloudTrail 审计（不记录查询文本 / URL / 原始网页内容）。
Web Search on Bedrock 把一件「人人都要自己拼」的脏活收编为平台能力，给做基础设施 / API 产品三条启示:① 把高频的「胶水活」收敛成一等能力，替用户消灭集成负担——过去接检索要选供应商、管 API key、写编排、处理重试与限流;Bedrock 把这些压成「加一个参数」，本质是识别到「几乎所有人都在重复造同一段胶水代码」，于是把它做进平台。找平台级功能，先看用户在反复自己拼什么。② 复用既有 API 形态，别让用户学新协议——直接嵌进 OpenAI 兼容 API 的 tools 参数，让已有代码近乎无改动就能用;能力再强，若要用户改协议 / 换 SDK，采用曲线就会陡峭。③ 结果要「自带可信凭据」，把可验证性做进返回值——强制回带 url_citation 引用注解，让「答案从哪来」可追溯;涉及事实性输出的能力，引用与审计不是附加项，而是能不能被企业采用的前提。把高频「胶水活」收敛成一等平台能力（接搜索 = 加一个参数）;复用既有 API 形态（OpenAI 兼容 tools 参数），不逼用户学新协议;结果「自带可信凭据」（url_citation 引用注解），可验证性做进返回值;默认零数据外泄 + CloudTrail 审计，合规作为默认交付;server-side 闭环，消除客户端 tool-use 循环 / 重试 / 限流负担;能力启用「单参数化」，把集成成本压到最低。
来源：aws.amazon.com · Introducing Web Search on Amazon Bedrock for foundation model grounding
Amazon Bedrock · 自动推理策略优化 AWS 2026.08.03
  • 把「诊断—修复」循环自动化（08.03）—— AWS ML Blog 记录:过去优化自动推理策略要手动诊断、手改、重测，现在 refinement engine 会自动诊断失败的测试并提出 formal-logic 修复，内部反复模拟直到收敛。
  • 两种模式对准两类问题（08.03）—— Iterative Refinement 处理「规则问题」（逻辑不对，提出增 / 改 / 删规则或变量）;Ambiguous Variable Refinement 处理「语言问题」（自然语言到 formal logic 的翻译有歧义，提出更清晰的变量描述）。
  • 每一项改动生效前都要人工 Accept（08.03）—— 引擎收敛后弹出「Review policy changes」界面，用户可 Accept 或 Discard，接受后才写入 DRAFT 策略;诊断与修复自动化，但「改不改」的最终决定权留在人手里。
这次更新是「AI 帮你改 AI 的规则」，恰好给「AI 参与关键决策」立了一条清晰的边界原则:① 自动化负责「诊断 + 提案」，人类保留「批准」这最后一道闸——引擎可以自己跑测试、模拟、收敛出一版修复，但每一项改动都要经过「Review policy changes」由人 Accept / Discard 才生效;凡是改动会影响系统行为边界（策略 / 权限 / 规则）的场景，AI 都应止步于「建议」，把「拍板」留给人。② 把问题「归类」再给方案，让人看得懂 AI 在改什么——区分「规则问题（逻辑错）」与「语言问题（翻译有歧义）」两种模式，等于先告诉人「这是哪一类毛病」再给修复;可解释的前提是可归类，别把一堆改动混成一锅让人无从判断。③ 改动写进 DRAFT 而非直接上线，给一个「可反悔」的暂存态——接受后先落到草稿，是在自动化与生产之间留一层缓冲;高影响改动应默认经过「暂存 → 复核 → 发布」而非一步到位。自动化止于「诊断 + 提案」，人类保留「批准」最后一道闸（影响行为边界的改动尤其）;把问题先「归类」再给方案（规则问题 / 语言歧义），可解释建立在可归类之上;改动先写 DRAFT 草稿、非直接上线，留「可反悔」暂存态;每项变更逐条 Accept / Discard，而非整包接受;引擎内部反复模拟至收敛，只把结果交给人评审（降低人的认知负担）;高影响操作走「暂存 → 复核 → 发布」而非一步到位。

AI 原生入口 · 数据侧

Amazon Quick · 数据到分析的自然语言入口 — 从「找数据」到「问数据」的入口重构

Amazon Quick · Agentic Catalog Experience AWS（预览） 2026.07.31
  • 用自然语言「描述需求」代替「翻目录找表」（07.31）—— AWS ML Blog 记录:data curator 可用自然语言描述数据需求，Quick Agent 借上游全部元数据浮现相关表;把「在庞杂 catalog 里逐层找表」的活变成「说清楚我要什么」。
  • 批量创建资产，并自动继承上游语义（07.31）—— Agent 规模化创建 Catalog-Generated Datasets:表 / 列的业务与技术描述继承进 Datasets，主外键关系继承进 Topics（预置 join 的多数据集构造）;上游 catalog 仍是唯一事实源（DirectQuery、只读元数据）。
  • 预览覆盖 Glue 与 Databricks Unity Catalog（07.31）—— 当前预览支持 AWS Glue Data Catalog 与 Databricks Unity Catalog;Amazon Quick 定位为上游元数据的「消费方」而非又一个 catalog，不复制数据、只消费上下文（自动同步在路线图上）。
Agentic Catalog 把「数据资产的分发入口」从「翻目录」重构为「问需求」，给做工具 / 平台入口三条启示:① 让用户「描述目标」而非「操作路径」，把检索负担交给 Agent——curator 说清要什么、Agent 借元数据浮现相关表，等于把「在层层目录里找」的认知负担转移给系统;凡是要用户熟悉复杂结构才能上手的入口，都值得用「自然语言描述目标」重做一遍。② 复用上游既有语义，别让用户重新标注一遍——表 / 列描述、主外键关系直接继承进 Datasets 与 Topics，是承认「上游 catalog 已经沉淀了大量语义」，接过来用而不是从零再造;好入口是「站在既有资产上」的，不是另起炉灶。③ 明确「谁是事实源」，消费而不复制——上游 catalog 保持唯一事实源、Quick 只读消费，避免数据 / 语义的多副本漂移;跨系统协作时，先讲清「谁拥有真相」，是可信度的地基。让用户「描述目标」而非「操作路径」，检索负担交给 Agent;复用上游既有语义（表 / 列定义、主外键关系）继承进资产，不重复标注;明确唯一事实源、只读消费不复制，避免多副本语义漂移;高频「找数据」重构为「问数据」的自然语言入口;资产可批量生成（Datasets / Topics 预置 join），降低起步成本;定位为上游元数据「消费方」而非又一个 catalog，减少生态重复。

对我们的启示

从 07.30 ~ 08.05 这一周产品动态中提炼的 4 条具体、可执行的设计建议

Insight · 01
↗ ChatGPT 桌面端 · 上下文就地带入
让上下文「就地带入」，别让用户搬运
ChatGPT 桌面端这次的浏览器 / 多仓库 / 图像编辑更新，底层是同一条主张——助手贴着用户已有的工作现场，而不是把人拽进新界面:① 凡是要用户手动复制粘贴搬运上下文的地方，都是可被「就地带入」替代的摩擦点——@提及标签页、带入高亮文本、右键 Ask ChatGPT，都是把「眼前正在看的东西」一键喂给助手。② 多目标操作要「一处纵览」，消灭视图切换——多仓库 diff 收进一个 Review、生成图进一个 viewer 跨图评论，让审阅 / 批处理场景不用切来切去。③ 编辑要「不离开主流程」——targeted edits 就地完成，减少「跳出去改完再回来」的断点，保持心流。上下文「就地带入」优先（@提及 / 带入高亮 / 右键唤起），减少手动搬运;多目标操作「一处纵览」消灭视图切换（多仓库 diff / 跨图评论收进一屏）;编辑「不离开主流程」（targeted edits 就地完成），保持心流;浏览历史等既有信息可被助手按需检索，历史即上下文源;近期需关注项汇总为 Activity view，降低找回成本;助手贴合既有工作现场，而非另造新界面。
Insight · 02
↗ AWS 自动推理策略 · 人类保留批准闸
AI 负责诊断与提案，把「批准」留给人
Bedrock 自动推理策略优化把「诊断—修复」循环自动化，但每一项改动生效前都要在「Review policy changes」界面由人 Accept / Discard:① 凡是改动会影响系统行为边界（策略 / 权限 / 规则）的场景，AI 都应止步于「建议」，把「拍板」留给人——引擎可以自己跑测试、模拟、收敛出修复，但不越过审批这道闸。② 把问题先「归类」再给方案，让人看得懂 AI 在改什么——区分「规则问题（逻辑错）」与「语言问题（翻译歧义）」，可解释的前提是可归类，别把一堆改动混成一锅。③ 改动先写 DRAFT 草稿而非直接上线——在自动化与生产之间留一层「可反悔」的暂存态，高影响改动走「暂存 → 复核 → 发布」而非一步到位。自动化止于「诊断 + 提案」，人类保留「批准」最后一道闸;影响行为边界（策略 / 权限 / 规则）的改动尤其不可越审批;问题先「归类」再给方案，可解释建立在可归类之上;改动先写 DRAFT 草稿、非直接上线，留「可反悔」暂存;逐条 Accept / Discard，而非整包接受;高影响操作走「暂存 → 复核 → 发布」。
Insight · 03
↗ Web Search on Bedrock · 胶水活收敛为一等能力
把用户反复自拼的「胶水活」收编成平台能力
Web Search on Bedrock 把「接检索」这件人人都要自己拼的脏活——选供应商、管 key、写编排、处理重试限流——压成「加一个参数」:① 找平台级功能，先看用户在反复自己拼什么——当几乎所有人都在重复造同一段胶水代码，就该把它做进平台，替用户消灭集成负担。② 复用既有 API 形态，别逼用户学新协议——直接嵌进 OpenAI 兼容 API 的 tools 参数，让已有代码近乎无改动就能用;能力再强，若要改协议 / 换 SDK，采用曲线就会陡峭。③ 结果要「自带可信凭据」——强制回带 url_citation 引用注解 + CloudTrail 审计，让「答案从哪来」可追溯;涉及事实性输出的能力，引用与审计是能否被企业采用的前提，而非附加项。把高频「胶水活」收敛成一等平台能力（接搜索 = 加一个参数）;复用既有 API 形态（OpenAI 兼容 tools 参数），不逼用户学新协议;结果「自带可信凭据」（url_citation 引用注解），可验证性做进返回值;默认零数据外泄 + 审计，合规作为默认交付;server-side 闭环，消除客户端重试 / 限流负担;能力启用「单参数化」，把集成成本压到最低。
Insight · 04
↗ ChatGPT 大段粘贴 · 默认替用户挡隐性代价
好的默认，主动规避用户意识不到的负面后果
ChatGPT 把「粘贴超 10k 字符」默认转为附件，替用户挡下一个看不见的坑——大段文本会悄悄吞掉 context window、拖累回答质量，而普通用户根本感知不到:① 好的默认应主动规避用户意识不到的隐性代价——不是等用户踩坑再补救，而是在默认行为里就把负面后果消化掉。② 自动化必须留「一键还原」的退路——「Show in text field」保证自动转换不是强制;凡替用户做决定的自动行为，都要配一个低成本的撤销 / 还原入口，让「智能」不等于「霸道」。③ 被验证的体验应「默认扩展」到高价值场景——先在其它档位跑通、再补齐到 Enterprise / Education;体验的一致性本身就是企业级信任的一部分。好默认主动规避「隐性代价」（大段粘贴吞 context window 不可感知）;自动化必配「一键还原」退路，智能 ≠ 霸道;被验证体验「默认扩展」到高价值 / 强治理场景;触发阈值清晰可预期（>10k 字符），行为不玄学;长内容降级为可折叠附件，保持输入区干净;跨档位体验一致性作为企业级信任的一部分。
