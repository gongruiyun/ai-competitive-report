ChatGPT OpenAI 2026.07.16
  • ChatGPT / Codex 全局切换器（07.16）—— 官方 Release Notes 记录桌面端顶部新增 ChatGPT / Codex 全局切换，ChatGPT 内再分 Chat / Work 两栏，把「对话」与「工作」两类使用场景在同一入口里显式分层。
  • Unified Recents 统一近期列表（07.16）—— 近期使用项被合并进统一的 Recents，跨 Chat / Work 的历史都能在一处找回，降低「刚才那条在哪个模式里」的检索成本。
  • Cloud 任务同步 · Local 任务本地留存（07.16）—— 跨设备的 Cloud 任务可同步，Local 任务留在本机；桌面端用「同步范围」区分任务的可移动性，而非笼统地全部上云。
ChatGPT 这批桌面体验更新，核心是把「一个 App 承载多种使用场景」这件事的信息架构讲清楚，可提炼三条:① 多产品线合并要「顶层切大类、次层切模式」——ChatGPT / Codex 全局切换 + Chat / Work 二级分栏，是「多产品线合一」的正解:顶层切产品大类、次层切使用模式，而不是把所有东西塞进一个扁平列表让用户自己找。② 跨模式的历史必须能「一处找回」——Unified Recents 把 Chat / Work 的近期项合并，解决的正是多入口产品最典型的痛点:用户记得「做过」但记不清「在哪个模式做的」；统一近期列表就是那把万能钥匙。③ 任务的「同步范围」应作为一等属性显式呈现——Cloud 任务可跨设备、Local 任务留本机，这不只是同步体验，更关系到用户对「我的东西在哪、会不会被上传」的掌控感;用图标 / 标签把同步范围标清，比默认全同步更值得信任。多产品线合并 = 顶层全局切换器(ChatGPT / Codex)+ 二级模式栏(Chat / Work)，常驻不折叠;Unified Recents 跨模式合并近期项(一处找回，不按模式分裂);任务同步范围显式化:Cloud(可跨设备)/ Local(留本机)用图标区分;切换器状态要「记住上次所在模式」(减少重复切换);近期列表支持按模式 / 时间 / 项目过滤;同步范围可在设置里逐项管控(掌控感 > 默认全同步)。

Gemini Google 2026.07.16 ~ 07.21

Kimi K3 Moonshot AI 2026.07.17 ~ 07.20
  • Kimi K3 发布即成中国开源模型焦点（07.17）—— The Verge 报道 Moonshot 在周五发布 Kimi K3，并与阿里 Qwen 一同把中国开源大模型推到台前;K3 以强代码能力和开放策略成为本周开源阵营的主角。
  • 需求激增，暂停新用户订阅（07.20）—— The Verge 报道 K3 发布后需求接近当前容量上限，Moonshot 暂停新订阅，并表示新的订阅名额会分批开放。
  • 开源路线成为差异化信号—— The Verge 报道 Moonshot 将 Kimi K3 描述为拥有 2.8T 参数的开源系统，与阿里 Qwen 一起强化了中国模型厂商「公开可用 / 可自部署」的路线差异。
Kimi K3 从「发布即爆红」到「暂停新订阅」，给做高需求 AI 产品的团队三条现实教训:① 容量不足时，「诚实限流 + 说明原因」远胜「静默降级」——明确告诉用户需求已接近容量上限，并说明新名额会分批开放，比让用户遇到超时 / 报错、老用户体验劣化要体面得多;把「暂停」讲成「为了保住体验」，就能把负面转成信任。② 「暂停新订阅」页面本身就是一次品牌沟通——不要只甩一个「暂不开放」，要给等待名单、预计恢复信号、以及「为什么这么做」的解释;把限流页做成「我们很火 + 我们很负责」的双重信号。③ 开源分发会放大容量预期——当模型被定位为公开可用、可自部署的开源路线时，用户会默认它更容易获取;托管端若容量有限，就更需要把「托管服务容量」与「模型开放路线」讲清楚，避免期待错位。容量不足优先「诚实限流 + 原因说明」而非静默降级;「暂停新订阅」页配等待名单 + 恢复信号 + 原因;老用户体验优先级 > 新用户拉新(高峰期明确取舍);限流 / 排队状态实时可见(别让用户反复试);开源模型需区分「权重开放 / 托管容量」两套承诺;容量恢复用批次节奏公示(降低反复刷新成本)。

Google · Gemini 3.5 Flash Cyber（安全场景模型） Google 2026.07.21
  • 更便宜的安全专用模型 3.5 Flash Cyber（07.21 The Verge）—— Google 面向安全场景推出性价比更高的 Gemini 3.5 Flash Cyber，让「安全 / 威胁分析」这类高频、成本敏感的企业任务用得起专用模型，而非都压在旗舰上。
  • 「便宜 + 专用」是企业采买的现实诉求—— 相比通用旗舰，场景专用模型把「单位任务成本」压到企业能规模化跑的水平;云侧客户更关心「这个任务用哪个档最划算」，而不是单一最强模型。
  • 旗舰跳票下的「稳定档」托底—— 在 Gemini 3.5 Pro 仍未上线的背景下，3.5 Flash Cyber 这类可立即交付的场景模型，为企业侧提供了不依赖旗舰节奏的确定性选项。
从企业 / 云控制台视角，3.5 Flash Cyber 这类场景专用模型印证两条 UX 走向:① 模型选型要从「列一堆模型」进化到「给决策建议」——控制台不该只把通用 / 安全 / 轻量档平铺，而应按「你的场景 → 推荐档位 → 预估成本」做引导式选型;企业用户要的是「帮我选」，不是「给我看目录」。② 降本要能「被算清」:省钱要在控制台可见——「更便宜的安全模型」对企业最有说服力的呈现，不是发布稿里的形容词，而是账单页里「同任务同比节省」的对比;企业采购决策靠数据。第三条:安全 / 敏感场景模型要标清适用边界，避免被误用于非目标任务。模型选型 = 引导式(场景 → 推荐档 → 预估成本)而非平铺目录;成本预估器挂在模型选择页(选型即见账单);场景专用模型标清适用边界(安全 / 威胁分析等)避免误用;「稳定档 / 场景档」与旗舰并列(不依赖单次旗舰节奏);同任务跨模型成本对比可视(省多少一目了然);高敏感场景模型准入 + 用量留 audit trail。

AWS 这条更新的 UX 价值不在「又多一个文档」，而在把开发者上手路径产品化:① prompt 正在成为新的配置界面——以前接入云服务要读文档、装 CLI、配权限、抄命令；现在 AWS 把这些步骤收敛成 Lambda 控制台里的「Copy agent prompt」，让用户把配置意图直接交给 coding agent 执行。对 Agent 产品来说，prompt 不再只是输入框里的文本，而是可复制、可版本化、可分发的配置资产。② 开发者体验要从「教你怎么配」升级为「给你一段能跑的配置」——覆盖 Claude Code、Cursor、Copilot、Codex 等多工具，说明云厂商不能押注单一 IDE，而要提供跨工具的统一入口。③ 控制台按钮与 MCP server 是一体体验——Copy prompt 只是前门，后面接的是 Serverless MCP server 与 AWS knowledge；这类能力必须在界面上说清「会访问什么、会配置什么、权限边界是什么」，否则一键越方便，安全焦虑越高。Agent 配置入口 = 控制台按钮 + 可复制 prompt + 可审计权限说明;prompt 作为配置资产需版本号 / 适用工具 / 最后更新时间;多 IDE 支持用同一套 setup guide(Claude Code / Cursor / Copilot / Codex 等);MCP server 接入前展示权限边界(会读什么 / 能改什么);一键配置后给 checklist(已装组件 / 待授权项 / 验证命令);开发者上手从「读文档」变「复制可运行配置」。

对我们的启示

从 07.16 ~ 07.22 这一周产品动态中提炼的 6 条具体、可执行的设计建议

Insight · 01
↗ ChatGPT 桌面 · Chat / Work / Codex 分层
多产品线合一要"顶层切大类、次层切模式"
ChatGPT 桌面把 ChatGPT / Codex 做成全局切换器、ChatGPT 内再分 Chat / Work，给「一个 App 承载多种使用场景」立了范:① 多产品线合并的正解是分层，而非扁平堆叠——顶层切产品大类、次层切使用模式，用户永远知道"我现在在哪、能切到哪"，而不是在一个扁平列表里大海捞针。② 跨模式的历史必须能"一处找回"——Unified Recents 把 Chat / Work 的近期项合并，解决的正是多入口产品最典型的痛点:用户记得"做过"但记不清"在哪个模式做的"。切换器还要"记住上次所在模式"，减少重复切换的摩擦。多产品线合并 = 顶层全局切换器 + 二级模式栏(分层不扁平);Unified Recents 跨模式合并近期项(一处找回);切换器"记住上次模式"(减少重复切换);近期列表支持按模式 / 时间 / 项目过滤;场景分层要让用户"永远知道自己在哪";入口层级 ≤ 2 层(超过就该重新归类)。
Insight · 02
↗ ChatGPT 桌面 · Cloud / Local 任务区分
任务的"同步范围"应是显式、可管控的一等属性
ChatGPT 桌面把跨设备的 Cloud 任务与仅留本机的 Local 任务显式区分，这一步比它看起来更重要:① 同步范围关乎用户对"我的东西在哪、会不会被上传"的掌控感——用图标 / 标签把"可跨设备 / 留本机"标清，比默认全同步更值得信任;掌控感 > 便利性，尤其在 AI 处理个人 / 敏感内容时。② 在企业场景，同步范围直接是数据驻留合规的抓手——管理员需要能按"任务是否上云"配策略，这一属性应进 Admin 面板，而非埋在用户端;凡涉及数据去向的开关，默认要保守、可审计、可逐项管控。任务同步范围显式化:Cloud(跨设备)/ Local(留本机)用图标区分;同步范围可在设置里逐项管控(掌控感 > 默认全同步);企业侧同步范围进 Admin 策略面(按数据驻留分域);涉及数据去向的开关默认保守 + 可审计;"我的数据在哪"要一眼可查(不藏深层菜单);敏感内容处理默认本地优先。
Insight · 03
↗ Gemini 3.5 Pro 跳票 · 3.5 Flash Cyber / Google Vids
旗舰跳票怕的是"沉默",生成式人像默认要可溯源
Gemini 3.5 Pro 原定 6 月、本周仍未上线，同周 3.5 Flash Cyber 与 Google Vids 落地——这组对照给出两条硬原则:① 旗舰跳票最大的伤害不是延期，而是"沉默"；roadmap 要"宁可给区间不给死线，一旦定了就兑现或提前说明"，延期必须主动发进度，否则外界会用最坏方式脑补。用"能马上交付的场景 / 稳定档"（如 3.5 Flash Cyber）承接旗舰注意力，是聪明的发布节奏。② 生成式"本人出镜"必须把"可识别 / 可溯源"做成默认——Google Vids 的 personal avatars 让本人形象被 AI 生成，SynthID 水印不是可选项而是底线;凡涉及人脸 / 身份的生成，默认带标识 + 本人授权 + 可撤回应写进产品底线。Roadmap 用时间区间(如季度)不用死线;延期主动发进度说明(沉默 = 被脑补);发布节奏留"稳定档 / 场景档"托底(不押注单次旗舰);生成式人脸 / 身份默认带水印(SynthID)+ 明确告知;personal avatars 需本人授权 + 可撤回;安全 / 敏感场景模型标清适用边界。
Insight · 04
↗ Kimi K3 需求激增 · 暂停新订阅
容量不足时,"诚实限流 + 说明原因"胜过静默降级
Kimi K3 发布即爆红、因需求接近容量上限而暂停新订阅，并表示名额会分批开放——这套处理给高需求 AI 产品三条现实教训:① 容量不足时，"诚实限流 + 说明原因"远胜"静默降级"——把"暂停"讲成"为了保住现有体验"，就能把负面转成信任，比让用户遇到超时报错要体面。② "暂停新订阅"页本身就是品牌沟通——配等待名单、恢复信号、原因解释，做成"我们很火 + 我们很负责"的双重信号。第三条:开源分发会放大容量预期——当模型被定位为公开可用，托管端更要说明「权重开放」与「服务容量」不是同一件事，避免用户期待错位。容量不足优先"诚实限流 + 原因说明"而非静默降级;"暂停新订阅"页配等待名单 + 恢复信号 + 原因;老用户体验优先级 > 新用户拉新(高峰期明确取舍);限流 / 排队状态实时可见;开源模型需区分「权重开放 / 托管容量」两套承诺;容量恢复用批次节奏公示。
Insight · 05
↗ Figma Workflow lab · 设计→代码→PR
设计交付从单程变双向,设计系统要为"可回流"重构
Figma Workflow lab 演示"用 Figma Make 直接部署设计"、改动作为 PR 回流工程仓库，把设计交付从单程推向双向:① 当设计改动能直接生成 PR，组件命名、token 结构、状态定义就不再只是"给人看"，而是"给代码生成器读 + 给 diff 引擎比对"——命名和结构的严谨度直接决定 PR 质量，设计系统要按"机器可读契约"重构。② 双向 handoff 需要"谁是 source of truth"的显式约定——设计改一版、工程改一版，最大的坑是互相覆盖；必须设计"变更来源标记 + 冲突可视 + 合并策略"三件套。第三条:配合 Sightlines 这类内容，设计工具的价值正从"画布"延伸到"交付 + 协作"全链路。组件命名/token 作为机器可读契约纳入 lint;双向 handoff 三件套:变更来源标记 + 冲突高亮 + 合并策略;source of truth 显式切换(某组件以设计/以代码为准);PR 由设计生成时附"设计意图摘要"帮工程 review;handoff 历史 = 设计版本↔代码提交双向 timeline;工具价值从"画布"延伸到"交付 + 协作"全链路。
Insight · 06
↗ Tencent Design Miora · Agent Memory / Specialist Network
创意 Agent 要把"记忆、分工、画布"做成可控系统
Miora 不是单点生图工具，而是把 Agent Memory、Creative Specialists 和同一块 canvas 组合成创意工作室:① 记忆要可治理——记住品牌颜色、语气、审美偏好和"不要这样做"很有价值，但必须可查看、可编辑、可删除、可按项目隔离，否则长期记忆会变成黑箱。② 多 Agent 分工要可见——品牌、视频、3D、UI Specialist 如果只躲在后台，用户无法判断成本、进度和责任边界；画布应展示"哪个 Agent 正在处理哪个资产、用了哪些规则、下一步要确认什么"。③ 交付不是一张图，而是一套资产包——从 brief 到图片、视频、3D、UI 和品牌视觉全案，产品要内置一致性检查、局部编辑和最终交付包导出，而不是让用户自己拼装。Agent Memory 可见 / 可编辑 / 可删除 / 可按项目隔离;多 Agent 执行过程可视化(谁在做什么 / 成本多少 / 何时需确认);创意 Agent 产品结构 = brief 输入 + 任务拆解 + Specialist 分工 + 多模态 canvas + 局部编辑 + 交付包导出;品牌规则沉淀为可复用 Skill;局部编辑优先支持框选 + 标注 + 自然语言组合输入;全套资产输出必须做风格一致性检查。
